# Ghost Protocol — Open Questions

Items that require the user's input, or that the proof-of-concept (Roadmap M0) must resolve, before Phase A's scope or implementation can be considered final. Each links back to where it originates.

## Product / Legal

1. ~~**Storing other players' data.**~~ **Resolved.** PGCRs include teammates/opponents who never linked a Ghost Protocol account. **Decision:** storing display name and platform for non-linked participants (the current `activity_participant.bungie_destiny_user_info` design in `DATABASE_DESIGN.md`) is acceptable for Phase A as scoped — no further minimization needed.
2. **No deletion path for non-linked participants.** Open Question #1's resolution keeps a minimal display-name/platform snapshot for PGCR participants who never linked a Ghost Protocol account. Because they have no account with us, there's no self-service way for them to request its removal — unlike a linked user, who can disconnect/delete at will. **Accepted as out of scope for Phase A** (consistent with other third-party Destiny tools handling the same public API data) rather than left silently unaddressed; revisit if a takedown request is ever actually received.
3. **Monetization.** Bungie's ToS (`API_FEASIBILITY.md` §1) permits non-commercial use only without prior written permission. Phase A is free/non-commercial as scoped. **Needs confirmation:** no monetization (ads, subscriptions, paid tiers) is planned without first securing that permission — flag this explicitly if plans change later.

## API Behavior (resolved by the Phase A proof-of-concept, M0)

4. ~~**Activity history depth/retention.**~~ **Resolved (M0 PoC, 2026-11-14).** No numeric cap exists. `GetActivityHistory` terminates naturally when an otherwise-200 response's `activities` key is entirely absent (not an empty array) — confirmed by walking a real account (92,676 minutes played) back to its full history: 23 page fetches, 5,453 activities retrieved, date range 2017-09-10 to 2026-11-01 (essentially since Destiny 2 launched), zero 429s. One-account sample; the walk-until-boundary ingestion design in `SYSTEM_ARCHITECTURE.md` remains correct regardless of other accounts' depth.
5. ~~**Weapon-data coverage by activity mode.**~~ **Resolved (M0 PoC, 2026-11-17).** Sampled one PGCR each of Raid, Strike, PvP, Gambit, Dungeon, and Trials of Osiris from a real account/character and inspected `extended.weapons` for our own entry specifically: **all six categories came back populated**, none absent, none empty. One-account/character sample — the `weapon_data_status` (`present`/`absent`/`unknown`) tracking in `DATABASE_DESIGN.md` stays in the design as a safeguard for accounts or modes not yet observed.
6. ~~**PGCR retention window.**~~ **Resolved, as a lower bound (gap-closure step 8, 2026-11-21).** No official statement exists either way, but a real account's single oldest activity — instanceId `188706590`, period 2017-09-10 (essentially this account's full history, per #4's full-depth walk) — still returned a successful `GetPostGameCarnageReport` (HTTP 200). This establishes PGCRs remain fetchable at least ~9 years back on one account; it does **not** prove there's no purge window at all, only that this account's oldest activity hasn't fallen outside one (if one exists). The "ingest promptly, don't rely on backfill" design in `SYSTEM_ARCHITECTURE.md` stays as the safe default regardless.
7. ~~**Exact per-key stat names inside Bungie's generic `values` dictionaries**~~ **Resolved.** `activity_weapon_usage.values` keys confirmed (M0 PoC, 2026-11-17): `uniqueWeaponKills`, `uniqueWeaponPrecisionKills`, `uniqueWeaponKillsPrecisionKills`, consistent across all six sampled modes. `activity_participant.values` keys confirmed (gap-closure step 8, 2026-11-21), union across the same six modes: `kills`, `deaths`, `assists`, `score`, `completed`, `opponentsDefeated`, `efficiency`, `killsDeathsRatio`, `killsDeathsAssists`, `activityDurationSeconds`, `completionReason`, `fireteamId`, `startSeconds`, `timePlayedSeconds`, `playerCount`, `teamScore`; PvP/Trials only add `averageScorePerKill`/`averageScorePerLife`; team-based modes (PvP/Gambit/Trials, not solo Raid/Strike/Dungeon) add `standing`/`team`. **Mapping gotcha found in the same run:** every one of these — including int/bool-semantic ones like `kills` and `completed` — comes back as a JSON floating-point number (e.g. `kills: 475.0`, `completed: 1.0`) under `values.<key>.basic.value`. `DATABASE_DESIGN.md`'s promoted `kills`/`deaths`/`assists`/`score`/`completed` columns must be populated by explicit cast/round, never by assuming an integral JSON type. The top-level `standing` field (a sibling of `values`, per the schema) is populated in every mode including solo ones (defaulting to `0` there) — ingestion should source `standing` from that top-level field, not from `values.standing`, since only the former is universally present. Checked only for the requesting account's own PGCR entry, not teammates'/opponents' entries — relies on `DestinyPostGameCarnageReportEntry`'s `values` dict being the same schema for every entry regardless of whose it is, which hasn't been directly observed for a non-own entry.

## API Behavior, found during gap-closure (new, 2026-11-21)

14. **`DestinyActivityModeType` mode-code integers aren't officially sourced.** The numeric codes used throughout the PoC and relied on by `activity.mode`/filtering (Strike=3, Raid=4, AllPvP=5, Gambit=63, Dungeon=82, TrialsOfOsiris=84) were cross-confirmed only from two third-party community mirrors (`destinydevs/BungieNetPlatform`, `bungio`), never from an official Bungie source. A real attempt to verify them against Bungie's own generated API reference and its GitHub schema repo (gap-closure step 8) found the enum's member list unreachable within a reasonable search effort — not disproven, just unconfirmed. Mitigating evidence: all six codes were used to fetch real PGCRs in steps 5-8, and every one returned content consistent with its expected activity type (e.g. the "Raid" code's PGCR showed raid-length duration and kill counts), which is reassuring but not the same as an official citation. Re-verify by cloning `Bungie-net/api` and grepping its schema directly, or by contacts with the community library maintainers, before the `weapon`/`activity` modules hard-code the full ~90-value enum mapping.
